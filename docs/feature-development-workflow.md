# 功能设计与迭代流程

更新日期：2026-10-29。适用于本站后续功能、Agent 提示词、工具接口、采集和推荐逻辑的设计与迭代。

每个功能保留一份当前有效的设计文档。讨论得到的决定及时写入，实施完成后同步实际行为与验证结果，避免方案长期落后于代码。小调整更新原文及一条变更记录即可，不要求每次创建长报告。

## 每次迭代的步骤

1. **检查现状**：读取现有设计、相关实现和测试，区分用户已确认要求、建议默认值、待确认事项。外部参考记录具体版本与链接，不能当作本站已实现能力。
2. **更新设计**：写清本次用户场景、行为变化、范围、异常处理、接口/数据影响和验收条件。行为发生变化时改写当前章节，在变更表保留原因；不要只在文末累加互相矛盾的说明。
3. **实施必要改动**：每项改动对应场景与验收条件。复用已有能力，不顺带重构无关模块。普通实现细节可以自主决定；影响用户目标或关键约束时先澄清。
4. **验证**：业务规则用针对性测试；Agent 用固定证据案例与真实案例评测；界面用浏览器检查。失败、零结果、并发、身份/版本混淆和权限边界应按功能风险覆盖。
5. **收尾同步**：更新状态、默认值、部署/回退方式、测试结论、未完成项和迭代记录，README 链接到正确入口。结论以实际运行证据为准，设计完成不等于实现或上线。

设计和文档更新与实现放在同一次工作交付中，不延后为无期限待办。没有程序修改的方案轮次，验证文档、引用和现状对应即可，不为文档改动重复运行整套应用测试。

## 设计文档最小结构

- 标题、版本、更新日期和状态。
- 已确认用户目标与具体场景；建议和待确认事项明确标注。
- 当前行为与拟议行为，主要处理流程和 UI 交互。
- 数据/接口/权限边界，错误、重试、时效与成本处理。
- 实施步骤和可检查的验收条件。
- 简短迭代表：日期、版本、决定、原因/影响、验证结果。

状态使用：设计中、设计完成、实现中、已验证、已上线。涉及本机与服务器时分开记录；本机通过不等于服务器已部署。已有旧文档不需要为统一格式一次性重写，下次涉及该功能时同步。

## Agent 变更的专门要求

固定 prompt、工具 schema 和业务校验各有唯一有效来源。提示词在方案阶段可保存于 docs；落地后运行文件成为正文真源，文档链接它并记录版本，避免拷贝漂移。

提示词、模型配置、检索排序、字段融合或推荐规则变动时，记录预期改变的案例，并重跑相关评测。至少检查证据是否支持结论、未知是否误当事实、同名/版本是否混淆、重复是否被合并、失败是否被伪装成功。不以“输出 JSON 合法”代替准确性评估。

每个付费流程写明单次和全站预算、终止条件及错误处置。公开工具写明实际权限，不能只依赖 system prompt 限制访问。自动验证与人工评测分开记录，保留数据时点和剩余限制。

## 完成检查

- 当前文档与实际代码一致，计划内容没有被标成已实现。
- 用户反馈已纳入当前方案，过时决策有替代说明。
- 接口、prompt、默认值、部署步骤和来源链接可找到。
- 已运行检查有结果；未验证环境及未完功能明确保留。
- 涉及迁移时说明备份与回退；不把样例或评测数据写入正式库。

这套流程由根目录 [AGENTS.md](../AGENTS.md) 提醒后续开发遵循。它不新增每一步都要用户批准的流程；在已授权范围内继续工作，并及时更新可审查的结果。
