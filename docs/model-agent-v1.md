# 模型维护 Agent 使用说明

2026-10-30，v2.2（事务隔离与截断恢复）。已确认要求：每天北京时间 10 点采集；Models Table 为主，新闻补充其他模态；查库后直接建档或融合，不为每条新闻反复联网研究；新闻整理与模型库维护的 DeepSeek 对话全部开启 high 思考。v2.1 已在服务器运行；v2.2 本机 178 项后端测试和服务器备份副本回放通过，尚未部署服务器。后台新增区域的登录后视觉验收未完成。故障证据和部署边界见[本次修复记录](model-admission-recovery-2026-10-30.md)。

普通收录顺序为：保存原文 → 新闻分析时一并提取模型与字段证据 → 使用 MCP 共用检索函数查库 → 新模型建基础档案、已有模型补空或关联 → 编排新闻正文。每批至多 6 条新闻，正常收录复用已有分析调用，新增模型不需要独立研究及审核调用。

补提取结果逐条校验，第二次调用只重试失败条目；两次后仍无有效结果的条目标为待核对，正常条目照常保存。候选入库每条来源使用独立 Session 和 `BEGIN IMMEDIATE` 事务，在首次查库前取得写入资格；发生错误时回滚并关闭该 Session，再用新事务记录原始数据库错误，继续下一条，避免失效事务连带拖垮整批。事务内不调用外部 API。中英文机构对应及已确认别名参与检索，模型合并仍须证据核实，不能按近似名称自动删除。计划开放权重不标成当前已开放；框架和分辨率选项不单独当作模型。此前规则验收见[发布前整理](release-readiness-2026-10-29.md)。

## 已接通的流程

- Models Table 内外的模型都能从新报道取得补充。橘鸦“模型发布”保留栏目并逐条对账；AIHOT 模型栏目、其他来源的模型发布与有新增事实的主体模型一并处理，不把比较基线一律送去补查。
- 名称、机构和已确认别名参与检索。相似结果只作候选，同名歧义、尺寸或版本差异不能自动选第一条。模型输出的合并 ID 还需经过程序校验。
- 新模型须有含具体名称的原文证据，参数、许可证等未知项留空；已有模型只采用有引用的字段。查询工具与 MCP 复用 `backend/registry.py`，后台同进程调用，不额外启动 MCP 网络连接或让 LLM 复述查询结果。
- 有明确日期、对应模型名和正文引用的进展保存到模型时间线。权重和 API 状态的自动变更还要求引用位于档案已有的资料入口，且晚于已知状态；证据不足时保留更正建议。
- 人工接受更正的字段会锁定，后续自动结果不得覆盖。最初公布日期与后来的开放事件分别保存。
- 管理页面显示今日来源逐条对账、对应模型 ID、待确认和失败原因。检查完成不等于模型入库成功；无具体名称或身份歧义保留待确认，不静默丢弃。模型详情仍显示后续进展和关联新闻。

默认 `MODEL_AUTO_REVIEW_ENABLED=false`：不再扫描历史 Insights 触发付费复查，也不自动执行 7/30 天旧档案及 7 天草稿复查。升级时旧自动排队、重试、受阻及租约已过期的任务改为 `paused`，保留记录；管理员手动任务继续执行。显式改为 `true` 才恢复旧周期策略，不建议作为日常收录方式。

旧来源缺少结构化结果或提取校验失败时，只对待处理发布来源批量补提取：每批最多 6 条、一次调用加一次格式修复，不联网搜索；完成后保存内容指纹，重复运行零调用。新流程产生的未处理结果及失败记录跨日保留；升级前旧数据只自动核对当天发布或当天抓取的内容，不发起全历史回扫。空候选且仍是发布线索时在后台标为待核对，不无限自动重试。

管理员手动补查仍使用原有 DeepSeek 工具循环，每项最多 3 次搜索、4 次正文读取、3 轮工具决策，另有证据提取与审核请求；沿用租约、检查点、15 分钟期限及有限重试。它与普通收录的调用成本分开看。未引入新的 Agent 框架。

运行 prompt 的唯一来源：新闻与模型联合提取为 `backend/collector/insight_agent.py::SYSTEM_PROMPT`；缺失结果补提取为 `model_discovery.py::PROMPT`；手动联网研究为 `model_research.py::PROMPT`，手动入库判断为 `model_review.py::PROMPT`。`model_discovery.py` 的程序校验和 `SourceItem.model_discovery` 保存处置结果，不依赖 prompt 承诺查重。

## 后台思考模式

统一参数唯一来源为 `backend/collector/enricher.py::thinking_options`：明确发送 `thinking.type=enabled`、`reasoning_effort=high`，移除思考模式下不生效的 temperature。新闻分析、正文编排、模型补提取、HF 评测抽取、联网研究的工具决策及最终提取、模型审核都使用此配置。RSS 抓取、Models Table 同步及确定性查重入库不调用大模型；宠物助手不在本次修改范围内。用户已确认开启；输出余量和超时为实现默认值，无待确认事项。

保留现有 `deepseek-chat` 请求名；本轮小规模真实调用返回 `deepseek-flash`，并包含非空 `reasoning_content` 和 `reasoning_tokens`。这是当次服务响应，不把别名映射当作固定模型版本。官方参数与工具续接规则见[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)和[请求文档](https://api-docs.deepseek.com/api/create-chat-completion/)。

每次请求在原有答案额度上增加 8192 tokens，总输出额度同时覆盖思考和答案，并非分别锁定两者的额度：

| 调用 | max_tokens 总上限 |
| --- | --- |
| 新闻分析 | 18192 |
| 正文编排 | 16692 |
| 模型补提取 | 14192 |
| HF 评测抽取 | 8992 |
| 联网研究工具决策 | 11192 |
| 联网研究最终提取 / 模型审核 | 12192 |

SDK 单次请求超时设为 300 秒，SDK 自动重试仍为 0；业务原有有限重试、每日唯一任务、补查任务 15 分钟总期限及 3 次任务尝试保持有效。联网研究使用完整 `message.model_dump()` 回传工具轮的 `reasoning_content`，包括服务可能返回的空字符串，不将思考正文写入档案、日志或公开页面。单轮思考为空不代表请求关闭了 thinking。截断的研究决策直接失败，截断的 HF 评测按原失败规则返回空结果；模型补提取继续使用已有截断、结构和引用校验。

新闻分析和正文编排若收到 `finish_reason=length`，立即二分当前批次，最小为单条；单条仍截断则保留失败并处理其他批次。普通格式校验继续最多两次，401/402/403/429 停止后续请求。每个原始 6 条批次最多产生 11 个分组、保守请求上限 22 次；成功分组立即保存，任务重试跳过已完成条目。所有请求继续 high 思考且额度不变，不把截断结果当成功。该策略只在截断时增加小批次调用，没有每日金额硬上限；正文编排的个别失败不再阻止后面的正常批次。

预期提高复杂新闻与模型身份、版本、未来开放计划的辨别能力；未知仍须留空，现有引用、别名和幂等校验继续生效，不保证模型判断必然正确。思考增加输出 token 和等待时间。本次不新增任务或全库重跑；全站仍无硬性每日金额上限，成本受新闻条目量及人工补查量影响，默认关闭旧模型周期研究。部署后新处理和重试的任务使用新参数，已有完成结果不会自动重写。无数据库迁移、无新增依赖，需重启载入旧代码的进程；服务器重新 build/up 后生效。

## 信源恢复

首版采用可测试的故障分类与恢复规则。超时、连接中断和 5xx 有限重试；429 遵守 Retry-After 并延后运行；缓存始终保留原成功时间。401、402 和访问限制会给出诊断建议，避免连续重试。

模型补查服务的 401、402 或持续 429 会记录服务级暂停，任务保留为 `blocked`。修改凭据并重启模型 worker，或在后台点击“重新检测补查服务”，可恢复尝试；再次失败会重新暂停。新闻采集与其他可用来源继续运行。

暂不让 Agent 修改生产代码、自动替换未知信源或修改系统网络设置。解析器变化仍需使用失败样本修复并验证。首版没有引入付费的运维诊断 Agent。

## MCP 查询工具

通过官方 MCP Python SDK 提供四个只读工具：

| 工具 | 参数 | 返回内容 |
| --- | --- | --- |
| `search_models` | `query`、可选 `organization`、`limit`、`offset` | 候选模型、匹配依据、待确认记录 |
| `get_model` | `model_id` | 档案、别名、事件和冲突 |
| `get_evidence` | `model_id`、可选 `field`、`limit` | 字段证据、原文摘录和处理状态 |
| `get_source_health` | 无 | 来源诊断及补查服务状态，不含密钥 |

本机接入时，从项目目录运行：

```sh
python -m backend.mcp_server
```

MCP 客户端设置 command 为 Python 可执行文件，args 为 `["-m", "backend.mcp_server"]`，cwd 为项目绝对路径。`DB_PATH` 可指定数据库；默认使用项目的 `data/tracker.db`。这是 stdio 服务，正常运行时等待客户端协议消息，不能把它当普通聊天终端使用。

HTTP 接入先在 `.env` 设置独立的随机 `MCP_READ_TOKEN`，至少 32 字符，不要复用管理员密码或 DeepSeek API key，然后运行：

```sh
python -m backend.mcp_server --transport streamable-http --port 8001
```

客户端连接 `http://127.0.0.1:8001/mcp`，并配置 `Authorization: Bearer <MCP_READ_TOKEN>` 请求头。未提供正确令牌的请求返回 401。当前采用预配置 Bearer token，不包含 OAuth 登录服务；客户端需要支持自定义认证头。

Docker 可选服务默认不启动。配置好独立令牌后执行：

```sh
docker compose --profile mcp up -d --build
```

服务器地址为 `http://127.0.0.1:29012/mcp`，仅绑定回环接口，适合通过 SSH 隧道访问。第一版不提供公网 OAuth 接入，也不自动改主模型客户端配置。远程连接使用带端口的本地地址，保留 SDK 的 Host 校验。

MCP 当前不提供写入工具，维护由新闻管道和管理员入口触发。这样外部主模型可以先接入检索，受控写入接口在后续版本单独扩展。
